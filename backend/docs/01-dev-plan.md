## 1. 서비스 요약

SelfFit은 웹캠 기반 모의 면접 서비스다. 사용자가 면접 질문에 답하는 동안 AI가 **시선(안구 움직임)** 과 **얼굴 표정(감정)** 을 실시간으로 분석하고, 이상 행동이 일정 시간 지속되면 토스트 알림을 띄우며, 면접 종료 후 행동 분석 리포트를 제공한다.

| 구분 | 내용 |
|---|---|
| MAIN 기능 | 실시간 탐지 (질문 리스트 → 면접 진행 → 토스트 알림 → 최종 리포트) |
| SUB 기능 | 동영상 업로드 후 사후 분석 |
| AI 모델 | 안구 움직임 모델 1개, 얼굴 표정 감정 모델 1개 (7개 감정: 기쁨, 당황, 분노, 불안, 상처, 슬픔, 중립) |
| 스택 | FE Next.js (Vercel) / BE FastAPI (Render) / DB PostgreSQL / 인증 Supabase |

## 2. 백엔드의 역할과 경계

백엔드는 세 파트 사이의 **허브**다. 역할 경계를 먼저 명확히 해야 통합 지옥을 피할 수 있다.

```
[FE: Next.js]  ──HTTP/WebSocket──▶  [BE: FastAPI]  ──Python 함수 호출──▶  [AI: 모델]
     │                                    │
     │  Supabase Auth (로그인/토큰 발급)    │  Supabase JWT 검증
     └────────────────────────────────────┘
                                          │
                                     [PostgreSQL]
```

### 백엔드가 책임지는 것
- 인증된 사용자 식별 (Supabase가 발급한 JWT 검증)
- 면접 질문 관리 및 제공
- 면접 세션 생명주기 (생성 → 모델진행 → 종료)
- 실시간 분석 채널 운영 (프레임 수신 → 모델 추론 → 이벤트 판정 → FE로 전달)
- "일정 시간 관찰되면 알림" 규칙 엔진 (모델 출력의 시계열 판정)
- 면접 종료 후 리포트 집계 및 저장/조회
- 업로드된 동영상의 분석 파이프라인
- AI 모델을 서비스 안에 로드하고 호출하는 **통합 계층** (모델 입출력 계약 정의)

### 백엔드가 책임지지 않는 것
- 로그인 UI, 회원가입 화면, 소셜 로그인 흐름 → FE + Supabase
- 웹캠 접근, 프레임 캡처, 화면 렌더링 → FE
- 모델 학습, 데이터 전처리, 성능 개선 → AI(ML Engineer) 팀
- 단, 모델을 **서비스에서 쓸 수 있는 형태로 내보내는 규약**은 백엔드가 정하고 AI 팀이 따른다

## 3. 기능 요구사항 (MVP 범위)

우선순위: **P0** = 없으면 MVP 불가, **P1** = MVP에 포함하되 축소 가능, **P2** = 시간 남으면

| ID | 기능 | 우선순위 | 설명 |
|---|---|---|---|
| F-01 | 인증 연동 | P0 | Supabase JWT를 검증해 요청 사용자를 식별한다. 미인증 요청은 거부한다. |
| F-02 | 면접 질문 제공 | P0 | 질문 목록을 조회한다. 초기에는 고정 목록(seed 데이터), 카테고리 필터는 P2. |
| F-03 | 면접 세션 관리 | P0 | 세션 생성(질문 세트 선택) → 시작 → 질문 전환 → 종료. 세션 상태를 DB에 기록한다. |
| F-04 | 실시간 분석 채널 | P0 | WebSocket으로 FE가 보낸 프레임(또는 얼굴 크롭)을 받아 두 모델로 추론하고 결과를 돌려준다. |
| F-05 | 이상 행동 이벤트 판정 | P0 | 모델 출력이 일정 시간 이상 지속되면(예: 시선 이탈 3초, 부정 감정 5초) 토스트 이벤트를 발행한다. 임계값은 설정 가능해야 한다. |
| F-06 | 분석 로그 저장 | P0 | 세션 중 추론 결과와 이벤트를 시계열로 저장한다. 리포트의 원천 데이터. |
| F-07 | 최종 리포트 생성/조회 | P0 | 세션 종료 시 로그를 집계해 리포트를 만든다. 시선 집중 비율, 감정 분포, 질문별 요약, 이벤트 타임라인 등. |
| F-08 | 동영상 업로드 분석 (SUB) | P1 | 영상 파일을 받아 프레임 단위로 분석하고 동일한 리포트 형식으로 결과를 낸다. 처리 시간이 길어 비동기 작업으로 설계. |
| F-09 | 과거 리포트 목록 | P1 | 사용자의 이전 세션/리포트 목록 조회. 반복 연습 효과를 보여주기 위한 기반. |
| F-10 | 관리용 헬스체크 | P0 | 배포 상태 확인 및 모델 로드 여부 확인 엔드포인트. Render 헬스체크에 사용. |

## 4. 비기능 요구사항

| 항목 | 요구 | 근거 |
|---|---|---|
| 실시간 지연 | 프레임 수신 → 결과 응답 500ms 이내 목표 | 토스트 알림이 "지금 행동"에 대한 피드백이어야 의미가 있음 |
| 처리 프레임률 | 2~5 fps (30fps 전송 금지) | Render 무료/저사양 인스턴스는 CPU 추론이므로 프레임 수를 낮춰야 함. 시선/감정 판정에 30fps는 불필요 |
| 자원 제약 | Render 무료 티어 기준: 512MB RAM, 공유 CPU, 15분 유휴 시 슬립 | 모델 2개 합산 메모리와 콜드 스타트 시간을 반드시 측정해야 함 |
| 개인정보 | 얼굴 원본 프레임은 **저장하지 않는다**. 추론 결과(수치/라벨)만 저장. 업로드 영상은 분석 후 삭제 | 얼굴 영상은 민감정보. 저장 범위를 최소화해야 리스크가 낮음 |
| 보안 | 모든 API는 JWT 필수. 시크릿은 환경변수로만 관리, 저장소에 커밋 금지 | |
| 관측성 | 구조화 로그, 추론 시간 측정 로그 | 병목 확인용 |
| 이식성 | 개발 OS는 Windows 10, 배포는 Linux(Render). 경로/인코딩 차이를 코드에서 흡수 | 계획서 명시 |

## 5. 핵심 아키텍처 결정 사항

설계 단계 전에 팀과 합의해야 하는 결정들이다. 각 항목에 **권고안**을 적었다. 반대 의견이 없으면 권고안대로 설계에 들어간다.

### D-1. 실시간 추론을 어디서 하는가
| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 서버 추론 | FE가 프레임을 WebSocket으로 전송, FastAPI가 PyTorch/ONNX 모델 실행 | AI 팀 모델을 변환 없이 바로 사용. 로직이 한곳에 집중 | Render CPU 부하, 대역폭 소모, 동시 사용자 수에 취약 |
| B. 브라우저 추론 | 모델을 ONNX/TF.js로 변환해 FE에서 실행 | 지연 최소, 서버 비용 0 | 모델 변환 작업, FE 부담 증가, 브라우저 성능 편차 |
| C. 하이브리드 | FE에서 MediaPipe 등으로 얼굴 검출·크롭·다운스케일 후 작은 이미지만 서버 전송 | 대역폭 급감, 서버는 추론만 집중 | FE에 얼굴 검출 추가 필요 |

**권고: A로 시작하되, FE에서 프레임을 224px 수준으로 다운스케일하고 2~3fps로 제한한다.** MVP 통합 속도가 최우선이고, 모델을 만드는 팀과 서버가 같은 Python 환경이라 A가 가장 빠르다. 부하 문제가 확인되면 C로 이동한다. 이 이동이 쉽도록 서버 입력 규격을 "얼굴이 포함된 RGB 이미지"로 잡아 두면 FE가 크롭을 보내도 서버 코드가 바뀌지 않는다.

### D-2. 데이터베이스를 어디에 두는가
**권고: Supabase의 PostgreSQL을 그대로 사용한다.** 인증에 이미 Supabase를 쓰므로 사용자 ID(`auth.users`)와 서비스 테이블을 같은 DB에서 외래키로 연결할 수 있다. Render 무료 Postgres는 90일 후 만료되는 제약이 있어 부적합하다.

### D-3. 동영상 업로드 분석을 어떻게 처리하는가
**권고: MVP는 FastAPI `BackgroundTasks` + 상태 조회(polling) 방식.** 업로드 즉시 작업 ID를 돌려주고, FE가 상태를 주기적으로 조회한다. Celery/Redis 같은 별도 큐는 Render 인스턴스가 늘어나 MVP에 과하다. 단일 프로세스 한계는 문서에 명시한다.

### D-4. 모델을 어떤 형태로 서비스에 싣는가
**권고: FastAPI 프로세스 안에서 앱 시작 시 모델 2개를 1회 로드한다.** 별도 모델 서버(TorchServe 등)는 MVP 범위를 넘는다. 대신 백엔드에 `Predictor` 인터페이스를 두고, AI 팀이 내보낸 모델 파일을 이 인터페이스 뒤에 붙인다. 모델이 준비되기 전에는 **Mock Predictor**로 FE 통합을 먼저 진행한다.

### D-5. AI 팀과의 모델 인터페이스 계약 (초안)

**2026-09-04 확인 (상세는 `03-model-inventory.md`):** 전달받은 `AI모델.zip`은 NIA 2022 베이스라인이며, 설치가이드 PDF(YOLOv3 + gaze-angle)와는 다른 세트다. 서빙 대상은 zip 기준 아래 2개다. RIT-Net(안구 분할)은 시선 판정에 불필요해 제외한다.

| 항목 | 시선 모델: L2CS-Net | 감정 모델: Former-DFER |
|---|---|---|
| 구조 | ResNet50 + yaw/pitch 90-bin 헤드 | ResNet18형 + 공간/시간 트랜스포머 + fc(512, 5) |
| 가중치 | `l2cs_trained.pkl` 96MB | `former_trained.pth` 144MB (`module.` 접두사) |
| 입력 | 얼굴 크롭 1장, 448, RGB, ImageNet mean/std | 얼굴 크롭 **16프레임 시퀀스**, 112×112, RGB, `/255` |
| 출력 | yaw, pitch **각도**(도) | **5클래스** logit. 클래스 이름 미상 (AI 팀 확인 중) |
| 전단 | 얼굴 검출기 필요 (베이스라인에 없음). MediaPipe 예정 | 동일 검출기 공유 |
| 파일 형식 | ONNX 변환 시도 예정 | ONNX 변환 시도 예정 (einops 연산 확인 필요) |

이 사실이 서빙 설계에 주는 함의:
- 시선 출력이 각도이므로 "시선 이탈"은 **각도 임계값 × 지속 시간**으로 판정한다. 화면 좌표 변환과 캘리브레이션은 불필요할 가능성이 높다.
- 감정은 16프레임 묶음이 입력이므로 WebSocket 수신 프레임을 **링 버퍼**에 모아 1~2초마다 추론한다.
- 검증 스크립트만 있고 추론 함수가 없다. 백엔드가 `Predictor` 구현을 먼저 작성하고 AI 팀이 검증한다.
- 가중치 합 240MB에 torch 런타임까지 실으면 Render 무료 512MB를 넘을 가능성이 크다. ONNX Runtime 변환과 티어 검토가 필요하다.

> 모델 파일은 git에 직접 커밋하지 않는다. 배포 시 다운로드하거나 Git LFS를 검토한다.

### D-6. 실시간 통신 프로토콜
**권고: WebSocket 단일 채널.** 세션당 1개 연결, FE → BE로 프레임 메시지, BE → FE로 분석 결과와 이벤트 메시지. 메시지 형식은 설계 단계에서 JSON 스키마로 확정한다.

## 6. 개발 단계 (마일스톤)

날짜는 팀 일정이 확정되면 채운다. 순서와 완료 기준이 핵심이다.

| 단계 | 목표 | 완료 기준 | 의존성 |
|---|---|---|---|
| Phase 0. 기반 | 프로젝트 골격, 환경 설정, 인증, 헬스체크, DB 연결 | 로컬에서 서버 실행, JWT 검증 통과, DB 마이그레이션 적용 | Supabase 프로젝트 생성 |
| Phase 1. 세션 + 실시간(Mock) | 질문 API, 세션 API, WebSocket 채널을 **Mock Predictor**로 완성 | FE가 실제 모델 없이 면접 화면 전체 흐름을 돌릴 수 있음 | FE와 메시지 규격 합의 |
| Phase 2. 모델 통합 + 리포트 | 실제 모델 2개 연결, 이벤트 판정 규칙, 리포트 집계 | 실제 웹캠으로 토스트 알림과 리포트가 나옴 | AI 팀 모델 1차 납품 |
| Phase 3. 영상 업로드(SUB) | 업로드 → 비동기 분석 → 리포트 | 5분 영상이 완료까지 처리됨 | Phase 2 |
| Phase 4. 배포 + 검증 | Render 배포, 콜드 스타트/메모리/지연 측정, 임계값 튜닝 | 팀원 웹캠 테스트에서 지연 목표 충족 | Phase 2 |

**Phase 1까지는 AI 모델 없이 진행 가능**하다는 점이 중요하다. 모델 학습이 늦어져도 FE-BE 통합은 멈추지 않는다.

## 7. 리스크와 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| 감정 모델 5클래스 이름을 모름 | 출력 해석 불가, 리포트 제작 불가 | AI 팀 최우선 확인. 그 전까지 인덱스로만 로깅 |
| ResNet50@448 + 16프레임 트랜스포머를 CPU에서 돌리면 프레임당 1초 이상 가능 | 실시간 지연 목표 실패 | ONNX 변환, L2CS 입력 224 축소 실험, 감정 추론 주기 완화(2초) |
| 가중치 240MB + torch 런타임이 Render 무료 512MB 초과 | 서버 기동 실패 | ONNX Runtime만 탑재, 유료 티어 검토 |
| Render CPU에서 모델 2개 추론이 느림 | 실시간 지연 목표 실패 | 프레임률 하향, 입력 크기 축소, ONNX Runtime 사용, 최후에는 D-1의 C안 또는 B안으로 이동 |
| Render 무료 티어 슬립으로 첫 접속이 30초 이상 지연 | 시연 시 낭패 | 시연 전 사전 워밍업, 유료 티어 검토, 헬스체크 핑 |
| 모델 메모리가 512MB를 넘음 | 서버 기동 실패 | 모델 경량화 요청, 티어 업그레이드 |
| AI 팀 모델 납품 지연 | Phase 2 지연 | Mock Predictor로 Phase 1까지 완성해 두고, 모델 인터페이스를 조기에 고정 |
| 모델 입출력 규격이 팀마다 다름 | 통합 시 재작업 | D-5 계약을 설계 단계에서 문서로 확정하고, AI 팀이 이를 기준으로 export |
| 얼굴 영상 취급에 따른 개인정보 이슈 | 신뢰/법적 문제 | 원본 미저장 원칙, 업로드 영상 즉시 삭제, 사용자 동의 문구는 FE와 협의 |
| Windows 개발 / Linux 배포 차이 | 배포 시에만 터지는 버그 | 경로는 `pathlib`, 인코딩은 UTF-8 명시, 가능하면 Docker로 로컬 검증 |

## 8. 다음 단계(설계)에서 만들 산출물

1. **API 명세**: REST 엔드포인트 목록, 요청/응답 스키마, 에러 규약
2. **WebSocket 메시지 규격**: 프레임 메시지, 결과 메시지, 이벤트 메시지 JSON 스키마
3. **DB 설계(ERD)**: users(Supabase 참조), questions, sessions, session_questions, analysis_logs, events, reports, upload_jobs
4. **모델 인터페이스 명세**: `Predictor` 추상 클래스, 입출력 타입, 전처리 규약 (AI 팀 공유용)
5. **이벤트 판정 규칙 명세**: 어떤 조건이 몇 초 지속되면 어떤 토스트를 띄우는지, 임계값 표
6. **폴더 구조 및 개발 환경**: Python 버전, 패키지 관리, 린터, 테스트 프레임워크, `.env.example`
7. **배포 설계**: Render 설정, 환경변수 목록, 헬스체크 경로

## 9. 팀 확인 필요 사항

기획을 확정하려면 아래 답이 필요하다. 답이 없으면 괄호 안의 가정으로 진행한다.

1. **[AI 팀]** 감정 모델 5클래스의 이름과 인덱스 순서는? 기획서의 7개와 다르다 (가정: 답 오기 전까지 인덱스로만 표기)
2. **[AI 팀]** 전달받은 가중치를 그대로 쓰는가, 재학습하는가? 학습 데이터의 얼굴 크롭 규칙은? (가정: 그대로 사용, MediaPipe 박스 + 20% 여백)
3. **[AI 팀]** 1차 모델 납품 예상 시점? Phase 2 시작 시점을 정하는 데 필요
4. **[FE]** 프레임 전송 방식: 원본 다운스케일 vs 얼굴 크롭 (가정: 원본 다운스케일 224px, 3fps)
5. **[PM]** 토스트 알림 기준 초안: 시선 이탈 몇 초, 어떤 감정이 몇 초? (가정: 시선 이탈 3초, 불안/슬픔/분노 중 하나가 5초)
6. **[PM]** 리포트에 반드시 들어가야 할 지표 목록
7. **[PM]** 전체 일정과 중간 발표/시연 날짜 (마일스톤 날짜 확정용)
8. **[팀장]** Supabase 프로젝트를 누가 만들고 키를 어떻게 공유할지 (가정: 팀장 계정으로 생성, 키는 비공개 채널로 공유)
9. **[전체]** 기획서 PDF를 저장소 루트에 둘지 `docs/` 폴더로 옮길지 (권고: 루트 `docs/`로 이동)
